development workflow · claude harness

From ticket to review, the same way every time.

How a ClickUp card becomes reviewed, traceable code — seven stages where automation handles the repetitive work and the developer decides at the checkpoints that matter.

overview

Seven stages, three human checkpoints

1Branch from the ticket/git-cb
2Plan before coding/create-plan
✓developer validates the plan
3Implement, test-firsttdd
4Standardize the pull request/update-pr
5Automated multi-agent review/review-pr

Everything stays linked by construction: the branch name encodes the card, the PR links both, and the review request carries all three. Nothing depends on someone remembering a step.

stage 01 · branch

It starts with a ticket — and ends with a board that's already true

  • The card is read and classified: feature, fix, chore, or refactor
  • The branch name encodes the full context, machine- and human-readable
  • The card moves to “in progress” the moment work starts
feat/868g584nb-date-table
└ type  └ ClickUp id   └ what it's about
stage 02 · plan

Think first, code later

read the full ticket→ explore the codebase→ reuse-hunter+ security-sentinel→ draft the plan→ ✓ you validate→ .plans/
  • The full ticket is read — comments, attachments, subtasks — with questions asked when something is ambiguous
  • The reuse agent hunts existing code before anything new is proposed — flagging what belongs in shared packages
  • The security agent raises requirements while they're cheapest to address
  • Validated plans are saved to .plans/; /split-plan turns them into shippable slices — optionally ClickUp subtasks
GATE ✓

The developer validates the plan before any code exists. Gaps caught here cost minutes, not review cycles.

stage 03 · implement

One intention per commit

The plan is executed test-first, and commits never mix file types — history reads like a story, review stays surgical, reverts stay safe.

test(agent-service): add scorer fields for the new rule   ← failing test
feat(agent-service): implement the new rule              ← makes it pass
docs(agent-service): update the prompt                   ← separate concern
feat: tests + code + docs in one commit                  ← never
stage 04 · pull request

A PR that explains itself

  • SEMVER title following the shared commit conventions
  • Criteria of Done, the ClickUp link, and a plain-English “What this does”
  • Tables for any environment variables added or removed
  • Assignee set, pending comments addressed, automated reviewer triggered

Anyone — engineer or product — understands the change without leaving the page.

stage 05 · automated review

Machines review before humans do

  • Multi-agent pass, scoped to the branch: security, API contracts, patterns, simplicity, tests, dead code
  • Findings ranked Critical / High / Medium / Low
  • Approved findings become inline comments on the exact lines — written like a peer, not a bot
GATE ✓

Nothing is posted without the author's consent. The developer reviews the report, does a manual pass, and picks what reaches the PR.

stage 06 · manual qa

Automation proves the code — hands prove the feature

  • /manual-qa generates a step-by-step guide for the change: prerequisites, key action, sequential scenarios with concrete inputs and expected outputs
  • Plus a quick validation table and troubleshooting for the common failure points
  • Runs after the automated review — the code is already sound; this proves the behavior
GATE ✓

The developer walks through the product by hand and confirms the change works as intended before handing it off.

stage 07 · handoff

Closing the loop

  • The PR flips from draft to ready for review
  • A structured status comment is guaranteed on the ClickUp card
  • A short, human-sounding review request is generated with PR and card links
  • The developer posts it — the last step is deliberately human

Card, PR, and review request end the flow in sync: no orphaned tickets, no context-free review pings.

summary

Why this flow works

  • Same gates, every time — quality doesn't depend on remembering steps
  • Three cheap checkpoints — validating the plan, approving findings, and hands-on QA beat cycles spent fixing
  • Traceability by construction — branch → card → PR → review request
  • Automation reviews first — human review starts from a higher baseline
  • Humans stay in charge — every outward-facing action passes through the developer
